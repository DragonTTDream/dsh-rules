# 守卫该拦什么

守卫是**脱离模型**的一层：模型看不到它，也绕不过它。它只做一件事——
在工具真正执行前做一次单调检查，命中就拒，并把拒绝原因回灌给模型。

## 一、该下沉到守卫的判据

同时满足三条才下沉，缺一条就留在提示层：

1. **反复违反**：提示层已经写过，仍然会犯。
2. **可静态判定**：只用命令字符串 / 参数就能判，不需要理解意图。
3. **误拒代价低**：拒错的后果明显小于放过错的后果。

## 三、设计要求（这几条比清单本身重要）

1. **拒绝消息是路标，不是墙。** 回灌给模型的一句话要说清"为什么拒 + 该怎么做"，
   否则模型只会换个写法再撞一次。
2. **fail-open，绝不 fail-closed。** 守卫自身出错时一律放行并记日志；
   防线故障不能变成业务锁死。
3. **单调**：守卫在所有其他前置检查之后求值，不依赖它们的结果，也不被它们短路。
4. **可审计**：每次拒绝追加一行日志（时间、工具、命中原因、命令前缀）。
   没有日志的守卫等于没有守卫。
5. **有逃生口**：一个开关能降级成"只记日志不拒绝"，供观察期与新规则灰度使用。
6. **豁免白名单要显式**，不用正则宽匹配——宽匹配的豁免就是没有豁免。
7. **按目标判，不按动词判。** 出现 `rm -rf` 本身不是风险信号，**目标是什么**才是。
   动词判据对误杀零容忍：一次误判就让这条纪律在用户眼里整体失效。
   实测教训见 [`../incidents/INC-2026-10-21-guard-too-blunt.md`](../incidents/INC-2026-10-21-guard-too-blunt.md)。
8. **日志要脱敏，权限要收紧。** 日志记的是命令原文，而原文里常有口令。
   遮蔽规则要覆盖明文口令的常见形态，并且**大小写不敏感**。
   实测教训见 [`../incidents/INC-2026-10-21-guard-log-leak.md`](../incidents/INC-2026-10-21-guard-log-leak.md)。

还是"判别器坏了（该修代码）"——两者看起来一样，处理方式相反。
