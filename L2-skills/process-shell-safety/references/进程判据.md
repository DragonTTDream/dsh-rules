# 进程判据详解（铁律 1 的细节层）

> 何时读：写任何含「判进程在不在 / 选进程来杀」的命令前。正文只留结论，这里放完整做法与坑。

## 为什么 `pkill -f` / `pgrep -f` 会自杀

它们匹配**所有进程的完整命令行，包括运行这条命令的 shell 自己**。

```bash
pkill -f "venv/bin/python main.py"     # ❌ 匹配到调用它的 bash → 工具 shell 被 SIGTERM
pkill -f main.py                       # ❌ 匹配到容器里的 python main.py → 杀掉无关服务
until ! pgrep -f "foo"; do sleep 1; done   # ❌ 永不退出（pgrep 匹配到自己）
```

Linux 的 `pgrep`/`pkill` **不排除自身与祖先**；macOS/FreeBSD 默认排除。按 macOS 直觉写 Linux 命令必中招。

## 正确做法（按优先级）

1. **判「进程在不在」→ 只匹配可执行文件名，永不匹配命令行**：

   ```bash
   pidof github-mcp-server            # 在 → 打印 PID；不在 → 空、退出码 1
   pgrep -xc github-mcp-serv          # 兜底：comm 只留前 15 字符，必须用截断名
   ps -eo comm | grep -cx github-mcp-serv
   ```

   免疫原理：我的 shell 的 comm 是 `bash`，**永远不含目标名** → 结构上不可能自匹配。

   两个坑：
   - `pgrep -x` 拒绝 >15 字符的模式 —— `pgrep -xc github-mcp-server` 返回 **0**，
     **真进程在跑也报「不在」**，比自匹配更危险。
   - `pidof` 比对完整 basename。

   ⇒ **默认用 `pidof`，`pgrep -x` 只在名字 ≤15 字符时可靠。**

2. **PID 文件**：启动时 `echo $! > app.pid`，停止时 `kill "$(cat app.pid)"`。

3. **杀进程用精确 PID + comm 过滤**（光靠 `-f` 选进程会把祖先一起选中）：

   ```bash
   pgrep -f "venv/bin/python main.py --listen 127.0.0.1 --port 8188" \
     | while read p; do [ "$(ps -o comm= -p $p)" = python ] && kill "$p"; done
   ```

   先 `ps -o pid,ppid,cmd -p $PID` 看一眼再杀。

4. **只杀自己的后代**：`pkill -P $$`。

5. **判服务用 `systemctl is-active <unit>`；判 harness 管的模型用 `arbitrate_status`**
   （问服务管理器与 harness，不问 OS 进程表）。

## 双向军备竞赛

`kill <数字PID>` 会绕过 harness 的自杀防护，所以**先看清 PID 是谁**比依赖拦截更可靠。

## 本机踩坑实例

- `pkill -f main.py` 杀过 chef 容器的后端（容器内也是 `python main.py`，父进程 `containerd-shim`）。
- `pkill -f "venv/bin/python main.py"` 杀过工具自己的 bash（`[killed by signal: SIGTERM]`），
  导致后面的重启命令根本没跑，服务掉线。
