# 经验库（自我积累的经验系统）

> **一句话**：每次栽跟头都提炼成「症状 → 判据 → 正解」的一行，按**症状**索引；下次遇到同形状的失败，`grep` 一次就命中，而不是重新试错。

这不是第 6 层强制力，**是一个检索层**：

| | 强制层（L0–L3） | 经验库 |
|---|---|---|
| 作用 | 约束"该怎么做" | 回答"这次怪失败是什么、先查哪" |
| 进上下文吗 | L0 每轮进 | **只在失败时 grep**，平时零成本 |
| 谁执行 | 模型自觉 / 守卫代码 | 模型主动检索 |
| 增长方式 | 越加越贵，有硬闸门 | 越加越厚，但有生命周期与上限 |

**为什么不进 L0**：L0 每轮付费、有 14336 字节硬闸门；经验条目会持续增长，塞进去等于给每轮加税。L0 只留**一行指针**。

---

**写作标准（必读）**：[写法规格.md](写法规格.md)（11 条硬要求 + 五段模版） · [防复发规格.md](防复发规格.md)（判层四问 + 七步 + 负样本）。
**维护命令**：`bash bin/lint-gotchas.sh` / `bash bin/lint-gotchas.sh --refresh`。

## 一、目录与格式

```
经验库/
  README.md              ← 本文件（系统说明，改这里）
  INDEX.md               ← 症状索引，一行一条，**grep 的唯一入口**
  秒退无输出.md           ← 单条详情，四段式
  Windows引号被切.md
  归档/                   ← 超过两个会话没命中就移到这里
```

`~/.dsh/gotchas` 是指向本目录的软链，所以 `~/.dsh/gotchas/INDEX.md` 就是这份索引（L0 那行指针指的就是它）。

### INDEX.md：一行必须能 grep 到

```markdown
| 症状关键词（模型会写的词） | 判据 | 正解 | 详情 |
| 秒退 零输出 启动失败 0x2 9009 | 程序没起来，不是崩溃 | 先查 exit code / LastTaskResult | [秒退无输出.md](秒退无输出.md) |
```

**三条硬规则**：

1. **症状列写"模型遇到时脑子里会冒出的话"**——写「秒退」，不写「进程生命周期异常」。
2. **判据列写"怎么确认是这一类"**，一条就够。
3. **正解列写能直接抄的骨架**，不写故事、不写"要注意引号"这类空话。

### 条目：四段式

```markdown
## 症状
（原话级描述，含会出现在报错里的关键词）

## 判据
- 可指名的证据（exit code / 日志行 / 属性）

## 正解骨架
（可直接抄的写法）

## 反例
（明确标注"别再试这个维度"，防止三连栽）
```

## 二、怎么加（写入时机固定，否则会漏）

| 时机 | 动作 |
|---|---|
| **被用户纠正** | 当场加一条 `draft`（R-06 要求当场落盘） |
| **同一现象第 2 次出现** | 升 `active`，并考虑能否下沉 L3 |
| **成功用它解决一次** | 升 `active` |

**不写什么**：当时发生了什么（那是 `incidents/` 的事）；项目内事实（路径/端口/账号）；"要小心/注意"这类不可执行的句子。

---

## 三、生命周期与上限

| 状态 | 规则 |
|---|---|
| `draft` | 新建，未验证 |
| `active` | 成功命中并解决过一次 |
| `archived` | 连续两个会话没被命中 ⇒ 移入 `归档/` |

**过期判定**：`verified_at` 超过 `verify_sla_days` ⇒ lint 报红 ⇒ 降 draft（runbook 类 30 天，其它 90 天）。

**active 上限 20 条**。超了就把最久未命中的降级——否则这里会变成第二份 L0。

---

## 四、检索：grep，不用向量

```bash
grep -i -E "秒退|零输出" ~/.dsh/gotchas/INDEX.md
grep -i "引号" ~/.dsh/gotchas/INDEX.md
```

**为什么不用 embedding**：本机是单槽推理（一条 48GB 模型序列），embedding 检索会挤占推理；而症状词就是模型自己会说出来的词，`grep` 命中率足够。这是资源约束下的取舍，不是偷懒。

## 五、与其它层的关系（最容易搞混）

```
经验库里的一条 ──► 能用一条命令判定吗？ ── 是 ──► 下沉 L3 守卫（模型犯不了）
      │
      └──► 否 ──► 是方法论吗？ ── 是 ──► 下沉 L2 技能（动手时加载）
                            │
                            └──► 否 ──► 留在经验库（失败时检索）
```

**经验库是上游，不是终点。** 一条教训最理想的归宿是变成守卫或 lint 规则；留在库里的，都是暂时无法机检的。

## 外部参考（借结构，不抄正文）

社区早有等价物。**抄它们的正文 = 每轮 token 税且文化不同**；我们只借「结构的形状」。

| 参考 | 借什么结构 | 什么时候看 |
|---|---|---|
| [Model or Harness? 失败定位分类](https://arxiv.org/html/2607.28802v1) | **先判失败该归给模型还是载体**（见 [防复发规格.md](防复发规格.md) 第 3 步） | 想不清"该改 prompt 还是改守卫"时 |
| [Why Do Multi-Agent LLM Systems Fail?（MAST）](https://arxiv.org/pdf/2503.13657) | 多步/多智能体任务的失败按「分解 / 协调 / 验证」归因 | 任务跑飞但单步都对 |
| [awesome-agents-md](https://github.com/khasky/awesome-agents-md) | **core 常驻 + rules 按需加载**的分层对照 | 怀疑自己的 L0/L1/L2 分层是否有公认形状 |
| [anthropics/skills](https://github.com/anthropics/skills) | `skills/<name>/SKILL.md` 的标准结构（frontmatter=何时命中） | 新建/改造 L2 技能时 |
| [failure-modes.dev/library](https://failure-modes.dev/library) | 事故按「什么坏了 / 怎么级联 / 该带走什么」拆 | 写 `incidents/` 复盘时 |

**本机的增量在哪**（这些社区没有现成等价物，别指望抄）：
L3 守卫（`ctx.tools.guard` 上的计划门/卡片门/重复门）、单槽资源仲裁与 `arbitrate_run`、
`经验库` 的「症状→判据→正解 + verify_cmd」形态、以及一切带本机阈值的数字（14336 字节 / 900 秒 / effort=max）。
