# 输出通道黑洞：进程起来了，日志却一条没有

## 症状

- 日志文件**没生成**，或生成了但**一直是空的**
- 失败早就存在，但**从来没被记录过**；成功行也不在文件里
- 程序在控制台里手动跑能看到输出 → **双击/计划任务/服务里跑就什么都没有**
- 只有 GUI 程序（无控制台）才这样；同一个二进制在终端里跑正常

## 判据

三连，全部成立即是这一类：

1. **程序没有 stdout 接收方**：Windows GUI 子系统（`-H windowsgui` / `/SUBSYSTEM:WINDOWS`）没有控制台，
   stdout/stderr 句柄无效，写入**静默丢弃，不报错**
2. **错误/诊断走 stdout**：`fmt.Printf`、`fmt.Println`、`print` —— 它们写 stdout
3. **启动器只接了一路或没接**：只 `> out.log` 没有 `2>&1`，或者根本没重定向

一句话判据：**「进程起来了，但它的失败没有任何进程外的见证者」= 输出通道黑洞。**

## 正解骨架

**代码层（让诊断落到有接收方的通道）**

```go
// 启动第一件事：给日志一个确定落地的 sink，而不是指望 stdout 有接收方
f, err := os.OpenFile(logPath, os.O_CREATE|os.O_WRONLY|os.O_APPEND, 0o644)
if err == nil { log.SetOutput(f); defer f.Close() }
// 错误分支用 log（默认 stderr）或显式写 sink，禁止 fmt.Print*
log.Printf("fetch failed: %v", err)
```

**机制层（不让它再出现）**

```bash
# golangci-lint: 直接禁止 fmt.Print*
forbidigo -p '^fmt\.Print.*'
```

**运行时层（两路都接，别只接一路）**

```cmd
run.exe > out.log 2>&1
```

**验证层（失败路径必须有断言）**

```bash
# 故意造一次取数失败，断言文件里出现该行
grep -q 'fetch failed' out.log || { echo "日志断言失败：失败没被记录"; exit 1; }
```

**运维层（进程外见证者）**

> 每个失败路径都要有一个「进程外的见证者」：**文件 / 退出码 / 事件日志 / 指标**，四选一。
> 没有见证者的失败，运维上等于不存在。

## 反例

- 只 `> out.log`（少了 `2>&1`）—— 成功行在 stderr，照样丢
- 用 `fmt.Printf` 打错误 —— 写的是 stdout，GUI 子系统下直接被吞
- 改成 `log.Printf` 就以为完事 —— **若启动器没接 stderr，一样进不了文件**
- 只改代码不设 `log.SetOutput(file)` —— 依赖"环境会给管道"这个不成立的前提
- 用 GUI 提示框报错代替日志 —— 无人值守时等于没有见证者

## 边界

- 适用「**进程起来了，但输出没落地**」这一类
- **不适用**「进程根本没起来」——那看 [秒退无输出.md](秒退无输出.md)（先查 exit code）
- **不适用**控制台子系统程序 + 正常启动器：那种组合默认有接收方，不易踩
- 不覆盖「日志文件在写但内容错」——那是格式化/字段问题，判据看内容而非存在性
- 12-Factor 的「日志只写 stdout，别自己管文件」在这里有前提：**运行环境必须真的给你一根管道**；
  Windows GUI 子系统不满足该前提，此时必须显式设 sink
