# 经验条目的写法规格

> **用途**：经验库里每一条（以及任何要当 AI 提示词 / 本地存档的排障知识）都按这份规格写。
> **适用**：本仓所有 `经验库/*.md`，以及其它项目里同类"症状→判据→正解"的内容。
> **怎么验**：写完拿第 1 节的"判据"列逐条自检；任何一条不过就不算写完。

## 一、硬要求（10 条 + 1 条时间戳）

| # | 要求 | 判据（怎么验） |
|---|---|---|
| 1 | **类层在前，实例在后** | 删掉实例，规则仍可执行 ⇒ 合格；删了就废 ⇒ 你写的是事故记录 |
| 2 | **必须有可判定的检查** | 能给出**一条当场能跑的命令**？给不出 = 口号 |
| 3 | **症状用模型会产出的词** | 检索词取自报错原文 / rc / 字段名，不是分类名 |
| 4 | **祈使句 + 骨架** | 动作动词开头；「注意 / 小心 / 尽量」一律不许出现 |
| 5 | **写边界 + 反例** | 不适用场景写清；同一维度的错误排列组合列成"别再试" |
| 6 | **强度分级** | must / should / never；两条冲突时谁赢要写明 |
| 7 | **自包含** | 压缩后仍成立；不依赖"上一轮说过" |
| 8 | **长度预算（按 token，不按行数）** | 入口层 ≈500 token；单条 <2000 token；证据再下沉一层 |
| 9 | **可机检优先** | 能写成 lint / test 的，不许留成散文（散文会烂） |
| 10 | **去标识化** | 路径 / 主机 / 账号不进条目 |
| 11 | **可执行的验证时间戳** | front matter 三件套：`verified_at` / `verify_cmd` / `verify_sla_days`；**`verified_at` 由 `bin/lint-gotchas.sh --refresh` 跑过 `verify_cmd` 后自动盖**，禁止手写；本机验不了的写 `verify_cmd: skip` + `verify_note`，按 SLA 到期降 draft |

## 三、五段模版（可直接套）

```markdown
# <症状的一句话标题>

**状态**：active | draft（last_verified: YYYY-MM-DD）

## 症状
（模型会看到 / 说出的原话，含报错关键词、rc、字段名）

## 判据
（一条可执行检查 + 通过/失败各长什么样）

## 正解骨架
（能直接抄的写法，按稳健度排序）

## 反例
（这个维度上别再试的排列组合）

## 边界
（什么时候不适用，避免过度泛化）
```

## 四、写完必答的三问

1. 换掉实例（UTF-16 → CRLF → 行尾空格），规则还成立吗？成立 = 纪律，不成立 = 案例。
2. 这条能不能变成 lint / test / 守卫？能 ⇒ 下沉，别留在散文里。
3. 现在把它交给一个没上下文的同事，他能照做成功吗？不能 ⇒ 缺的是第 2 或第 3 节。
