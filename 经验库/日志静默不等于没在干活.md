# 日志静默 ≠ 没在干活（窗口到点返回也算事故）

**状态**：active（last_verified: 2026-10-23）

fault_layer: harness
fault_why: 窗口把"到点"当成"任务结束"交还控制权，而主对话与后台任务跑在同一条推理序列上

## 症状

- 「job.log 十几分钟没动一行，这任务是不是挂了？」「窗口超时返回了，应该没跑完吧？」
- 实际状态：进程树活着、CPU 在涨、引擎侧每步都在出 token，只是日志按设计**跑完才写**。
- 伴随现象：窗口返回后主对话恢复生成，引擎上两个会话交替，`reused` 从 ~98% 掉到 0，
  每次请求预填充从 2s 变成 44–51s（「交替抢模型」）。

## 判据

一条命令能同时看到三路，任一前进 = 活着；只看日志必误判：

```bash
ps -o pid,etimes,time,args -p <job pid>                                   # 存活 + 累计 CPU
curl -s 127.0.0.1:<engine>/metrics | jq '.requests[0:3][] | [.time,.prompt_tokens,.output_tokens]'
```

- 通过（= 在干活）：pid 在、CPU 时间涨、`prompt_tokens`/`output_tokens` 每步递增。
- 失败（= 真挂了）：pid 消失，或 CPU 与请求列表同时冻结 ≥ `stallMinutes`。
- **窗口返回 ≠ 任务结束**：返回后若 `ps -o pgid= -p <pid>` 还在、作业记录里又没有 `marker=`，
  那就是"返回了没跑完"，必须回到等待，不是收工、更不是杀进程。

## 正解骨架

1. 窗口侧：`timeoutSec`（≤900）只是**软预算**，到点只往 job.log 写一条进度、继续等；
   真正收尾只有三条 —— 拿到 `marker=` / 进程退出（script-died、no-start）/ 空转（stall，
   由 job.log 大小 + 工作目录 mtime + 进程树 CPU 三路判活）。硬上限 `hardCapSec` 到点才返回 timeout。
2. 万一还是返回了：窗口返回时给作业记录打 `windowReturnedAt`，`orphanJobs()` 据此认出孤儿；
   owner 会话的 `ctx.tools.guard` 除 `arbitrate_wait` 白名单外全部拒绝，拦截文案直接写出
   `arbitrate_wait({jobId, waitSec:300})` ⇒ 结构上只能回到等待。
3. 观察者侧：`arbitrate_wait` 只看 `waitSec` 与进程是否还活，活着就返回 `running`（done=false），
   **不许**被窗口自己的 deadline 提前掐断。

## 反例

- 拿 `tail job.log` 的静默当"任务死了"的证据 ⇒ 杀掉正在正常推进的任务（2026-10-23 实测提议过一次，被用户挡回）。
- 把"日志没写"当成脚本 bug 去改脚本 —— 真正原因是脚本按设计跑完才写日志。
- 到点返回后直接恢复主对话干活 ⇒ 自造两个本地客户端，两边都慢一倍以上。
- 用"再起一个等待窗口"来等 ⇒ 那个窗口被声明成 remote 后立即返回，等于没等。

## 边界

- 脚本**每步都写日志**的批处理任务，日志静默确实可疑：先用 CPU 路与引擎请求列表对拍，再判 stall。
- 远端主机上的活（不占本机推理序列）不适用本条：等待方可以短轮询，不必占住回合。
